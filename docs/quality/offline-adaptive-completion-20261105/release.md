## What changed

Same-account refresh retains usable posts, author data, thumbnails and media layout while fresh data arrives. Stable source identity prevents renewed authorization tokens from remounting a working image or video. A completed background cache download does not replace an actively playing network video. Known denial, logout, account change and source replacement invalidate affected content.

The route inventories cover the registered native screens, 105 member web pages and 35 operations pages. They distinguish content-preserving refresh, initial-load-only loaders, and intentional identity resets. See `../app-continuity-20261104/screen-inventory.md` and `../always-ready-20261105/web-admin-loading.md`. This is source and regression coverage. It does not claim that every route received a physical-device walkthrough.

Native and web cache eligible public-feed images and videos at their delivered original resolution. Native uses the actual iOS CryptoKit and Android Cipher AES-GCM implementations. SecureStore retains the master key, and derived object keys bind the account/session, media identity, storage path and immutable version. The encrypted budget is 128 MiB, each file is limited to 24 MiB, and opened plaintext is bounded to 32 MiB and eight files. Backgrounding removes opened plaintext. Logout or account replacement removes its key and index.

Web encrypts original bytes in IndexedDB with non-extractable AES-GCM keys. Its budget is 128 MiB, 24 files and at most 32 MiB per file. Only mounted media is decrypted, and blob URLs remain stable while unrelated downloads finish. The app shell is not newly made available offline.

Both media caches expire after 24 hours and require server-approved public-feed eligibility and immutable source versions. Private messages, limited-view media, administrative records, sensitive media and oversized files are excluded. Offline clients cannot learn revocations that happen after the last successful authorization check. Fresh uncached original files still require network transfer.

## Adaptive video and protected chat

The signing path now returns the immutable original version directly from the newly issued capability ticket. The additive `issue_content_media_delivery_v2` RPC delegates to the unchanged original issuer, then reads the exact ticket for the current user, session, object and expiry. Optional HLS readiness can no longer remove the original version on absence, failure or deadline expiry. A mismatched HLS version cannot replace the ticket authority. This fixes the observed refresh path that lost the decrypted local image and briefly showed blank media. The actual failing request body was not recorded, so a readiness timeout on that particular request is inferred rather than directly observed.

The signing path returns immutable source versions and optional prepared HLS hints for authorized capabilities. It checks at most 32 streams per 128-item batch. Its optional metadata budget is 500 ms. Deadline expiry retains the authorized original. Native feed, Discover, shared-post viewers, stories and memories, plus the corresponding web viewers, use prepared adaptive streams where supported. Published live clips and channel clips retain provenance, ownership, publication and lease checks.

The iOS story wrapper now waits for the actual AVPlayerItem readiness of an HLS stream. It no longer rejects an initially empty streaming asset. Generation and item-identity checks prevent an obsolete load from replacing the active item. Preparation gates the first graded frame and initial trim seek. Full Swift integration compilation passed for the exact current rendering-source hashes. The final eight-case graded runtime gate is recorded separately below.

Protected chat HLS uses a separate authenticated endpoint. Each manifest and segment request checks the live session, conversation permission, original source version, encoder lease and viewing grant. The generic media gateway does not accept private chat HLS or broaden its authorization cache. Limited-view HLS and original delivery reuse the same fixed-deadline request ID, so switching between them does not consume another view. Closure is terminal. Private media does not enter the public offline cache.

## Capacity decision

The unchanged foundation scenario passed all 1,200 offered reads with zero failures or dropped arrivals, plus 25 real refreshes during load. Steady service p95 was 35.38 ms and soak service p95 was 31.91 ms. These are isolated database/service measurements, not full-device startup times. Media admission and four real encode/decode probes also passed.

The expanded profile used 250,130 total posts, 128 authenticated actors, 32 read workers and a database restricted to two CPUs, 2 GiB and 60 connections. All 128 snapshots completed, and the slowest preparation took 4.594 seconds, below the unchanged eight-second per-job deadline. Total preparation took 144.088 seconds, or 0.888 snapshots/second. Early snapshots expired before readback, so the freshness gate failed. The intended steady/soak workloads were not reached.

The existing 45-second refresh cadence requires at least 2.844 snapshots/second for those 128 actors, approximately 3.2 times the measured preparation rate before extra headroom. The published exact-ranking fixes improve real bottlenecks and preserve canonical top-200 IDs/keys, authorization and bounded work. They do not establish the larger capacity target.

The expanded query/scheduler rollout is held. Production retains the existing schedule of one snapshot every ten seconds. No four-lane hosted schedule, resource upgrade or quota increase has been activated. The concrete next options are a separately authorized resource calibration with unchanged acceptance rules, or a reviewed architecture change that removes repeated per-viewer work while retaining exact ranking and invalidation. Details and original evidence are in `../../../tools/performance/measurements/capacity-operating-proposal-20261105.json`.

Five-million-DAU acceptance remains unproven. Provider reservations, approved operating budget, regional delivery/realtime evidence and a representative 24-hour authenticated mixed workload remain unverified. This release does not claim zero latency, universal offline media, every-route physical acceptance or the requested large-scale capacity.
