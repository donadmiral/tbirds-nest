## What this integration changed
- Separate the feed visibility thresholds for starting/stopping playback. A neighboring card cannot interrupt a manually chosen video. The selected Discover slide owns playback. A manual pause/end survives observers and delayed recovery. Renewed same-version capabilities preserve the active decoder. Replacement sources or session changes clear old playback state.
- Keep live player pause intent on renewed grants, native metadata events, retries, tab visibility changes and close. Rebuffering does not falsely mark an authorized viewer as having left. Native autoplay refusal is visible and recoverable.
- Require real covers for new video uploads in both Studio planners. Existing feed composers already capture covers. Newly published live clips carry their poster reference. A failed capture/upload cannot create a new coverless Studio attachment in the updated clients.
- A failed warm refresh displays a notice without moving the posts below it. Cloud testing reproduced the old video-tile placeholders on three of five production videos.
- Restore failed thumbnails after a temporary failure/new grant. Respect data saver, account and content identity, exact capabilities, and selected frame time. Unknown sources cannot share frames based only on a stripped query string. Never count a zero-dimensional video or an unpresented picture as a successful thumbnail.
- Retain both private-media authorization checks and the original 12-second startup deadline. At most one fresh read may retry a proven transport timeout, never a refusal, invalid result, cancellation or non-idempotent action. No capability, asset path or user identifier enters the added timing fields. After deployment, live observations included both recovered requests and requests that reached the original deadline. The upstream transport is not guaranteed error-free.

## Measured delivery time

From 17:19:47 to 17:23:41 UTC, the production media function recorded ten GETs: six HTTP 200 and four HTTP 206, with no failed request in that interval. The two compatible MP4 ranges took 3.742 and 11.988 seconds of function execution. The two private posters took 1.071 and 4.104 seconds. These are server execution times, not time to the first visible frame or a site-wide speed benchmark. The slow request aligns with a single scoped handler trace: its first revalidation timed out waiting for response headers at 8.003 seconds, then the bounded retry returned 200 in 2.147 seconds. The first Storage byte was available immediately after the final authorization. The handler was ready at 11.718 seconds against a 12-second startup deadline. This is correlated by time and isolate rather than a shared request ID. These startup fields do not measure transfer time to the viewer. This one observation does not establish a reason to skip the access check, change SQL or raise the deadline. See production-media-window.json.

## Acceptance boundary
Web and dashboard deployment, mocked browser testing, real signed-in web playback, native build generation, app-store publication and actual physical-device testing are distinct outcomes. A passing build does not update an already-installed phone. Cold media delivery depends on network conditions. A generated poster does not imply access to a deleted, revoked or unauthorized source. No public broadcast, real message, payment, financial transaction or change to anyone's account was required for the verification.
