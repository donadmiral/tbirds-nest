# Live runtime acceptance checkpoint

This checkpoint is a partial operational repair, not full product acceptance.

## Fixed and installed

The actual QA start attempt from build 18 hit PostgreSQL 42702 in live_streams.finish_control. The local variable and updated column were both named result. Both accepted and rejected provider requests could therefore fail to persist their completion. The guarded rename is installed in QA and production with unchanged permissions and provider-confirmation rules. The two migration filenames use the actual versions generated by the hosted migration service. Reapplying the second version is intentionally harmless.

Production live notifications were disabled. They are now enabled after checking that no active broadcasts existed. The existing maintenance, worker and interaction-flush jobs were re-registered without changing cadence. Automatic worker completion and five-second interaction runs were then observed. No retroactive notifications were sent.

## Evidence boundaries

Fourteen hosted-QA SQL checks passed inside a rolled-back synthetic transaction. They cover creation, scheduling, idempotency, accepted/rejected completion, leases, event transitions, follower eligibility, notification deduplication, access rules and chat creation. They do not test actual Daily, a physical phone, websocket delivery or push delivery. The added isolated PostgreSQL regression explicitly reproduces the old defect and exercises the real original function extracted from the portable migration.

No camera was remotely activated, no user broadcast restarted, no public test post published and no capacity limit raised. The temporary diagnostic endpoint was retired without executing a provider inspection. The new visual mockups remain design concepts, not delivered functionality.

## Required acceptance evidence before release

| Journey | Required observation |
| --- | --- |
| Start now | Preview with explicit camera consent, single start command, provider acknowledgement, signed started event, viewer receives frames and audio |
| Schedule | Future time saved, no camera activation, reminder honors preferences, host can start scheduled session |
| Failure recovery | Distinguish rejected request from ambiguous timeout, no endless Starting/Ending, no duplicate stream on retry, capacity released only after confirmed provider state |
| Chat and reactions | Two independent accounts exchange messages, bounded history, reconnect without duplicates, slow mode and moderation take effect |
| Follower alert | Confirmed live event creates one eligible alert, opt-out and blocked accounts excluded, device push arrives and opens the correct session |
| Viewer metrics | Real viewer session accounting, duplicate tabs/devices defined, reconnect and departure reconciled, counts labeled accurately |
| Clips | Authorized live/replay time range, queued rendering, finished assets, captions and cover, each enabled publication destination, device export |
| Admin | Scoped staff access, valid reasons for destructive actions, actual provider stop confirmation, audit record, failed-job visibility |
| Scale | Document peak concurrency and fanout assumptions, provider quotas, progressive authenticated load, viral room, reconnect burst, soak and recovery |

Five million daily users is not five million concurrent viewers. Neither target is certified by this checkpoint. Current admission is ten broadcasts, twelve stage members, twenty chat messages per second as configured, and two production clip jobs. A signed CDN test does not certify notification, database, chat or encoder capacity.
