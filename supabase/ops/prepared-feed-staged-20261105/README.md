# Prepared feed staged installation

This is an equivalent installation route for the reviewed source migration `20261105044917_prepared_feed_snapshots.sql`. Whole-query and combined-worker connector calls produced no result and no database commit. The installed foundation was retained. Subsequent source units keep individual payloads below 4,000 bytes while preserving original function bodies, access controls, and final atomic activation.

Apply the SQL files in `manifest.json` order with `apply_migration`. Inspect the schema stage comment and provider migration history after each call. A failed or interrupted call requires independent readback before any retry. The foundation is 6,096 bytes and had already succeeded before subdivision. No stalled call established that size was the cause.

All intermediate stages deny `PUBLIC`, `anon`, `authenticated`, and `service_role` access to the private schema and do not change the existing public feed. New public functions initially reside in the private schema. Stage 7 verifies the unchanged baseline feed definition, moves the original function to `prepared_feed.canonical`, moves the new dispatcher and control functions to their public names, installs invalidation triggers and grants access in one transaction. The temporary contract metadata table is removed. Preparation remains disabled.

Do not change or encode function bodies to alter the provider's approval classification. All seven provider SQL MD5 values in `qa-installation-before-optimization.json` match the source units exactly. That receipt records actual staged history, not a claim that the original single migration ran.

Rebuild deterministically with `node supabase/ops/prepared-feed-staged-20261105/build.mjs`. Verify with `node supabase/ops/prepared-feed-staged-20261105/verify.cjs` and `PREPARED_FEED_STAGED=1 node --test supabase/tests/prepared-feed-db.test.cjs`. The equivalence check compares function definitions, owners, ACLs, columns, indexes, policies, triggers, and settings, and verifies no public behavior or private access becomes active early.

After complete activation, install `20261105051142_prepared_feed_narrow_ranking.sql` and `20261105051152_prepared_feed_single_snapshot_rank.sql`, then `20261105051338_prepared_feed_bounded_hydration.sql` and `20261105051457_prepared_feed_client_capability_gate.sql`. These require the indexed-feed chain and deterministic-author-tie migration. They replace four hydrated ranking passes with one private 200-ID ranking proof and preserve current RLS, session claims, exact fallback ordering and the restricted rank owner. Run `PREPARED_FEED_NARROW=1 node --test supabase/tests/prepared-feed-db.test.cjs` for all 16 behavior cases. The small local database suite is not a capacity measurement. Keep the feature disabled until the isolated native PostgreSQL load gate and hosted functional smoke pass.
